스킬 묶음 해설

선택판에는 묶음마다 일부 스킬만 넣었습니다. 역할이 겹치는 스킬은 다른 스킬로 대신할 수 있어서 뺐습니다. 여기서는 각 묶음 저장소의 README와 스킬 설명(SKILL.md)을 바탕으로 전체 흐름과 스킬별 역할을 봅니다. 선택판 표시가 붙은 스킬은 다른 탭에도 나옵니다.

2026-11-07 각 저장소 기본 브랜치 기준. 설명은 원문을 우리말로 옮겨 줄인 것이며, 스킬 이름과 명령은 원문 그대로입니다.

Memory File

에이전트는 지난 대화를 기억하지 못하고 파일을 읽고 일합니다. 이 파일들이 에이전트의 기억입니다. Law에서 프로젝트 시작 때 반드시 해 둘 것을, 빠른 찾기에서 파일별 쓰는 때·명령·복사용 프롬프트를, 맥락 스킬에서 파일을 대신 써 주는 스킬을, 단계별 파일트리에서 단계마다 어떤 파일이 생기는지 봅니다.

프로젝트를 시작할 때 반드시 해 둘 것만 모았습니다. 핵심은 규칙마다 둘 곳을 나누는 것입니다. 문서(AGENTS.md)에 적은 지시는 에이전트가 놓칠 수 있으니, 매번 반드시 지켜야 하는 규칙은 설정 파일로 강제합니다.

① 규칙을 어디에 둘까

매번 반드시 지켜야 한다.claude/settings.json계약 파일 수정 금지, 비밀 파일 읽기 금지, 저장할 때 자동 정리. 권한(deny)과 훅으로 항상 실행

특정 폴더에서만 필요하다하위 폴더 CLAUDE.md예: src/components/CLAUDE.md에 UI 규칙. 그 폴더 파일을 읽을 때만 불러옴

.claude/settings.json뼈대같이

문서로 부탁하지 말고 설정으로 막습니다. deny는 계약 파일 수정과 .env 읽기를 막고, 훅은 파일을 고칠 때마다 Prettier로 정리합니다. git에 커밋해 팀이 같이 씁니다.

{ "permissions": { "deny": [ "Read(./.env)", "Read(./.env.*)", "Edit(/specs/**/contracts/**)" ] }, "hooks": { "PostToolUse": [ { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" } ] } ] } }

jq와 Prettier가 설치돼 있어야 합니다. 계약을 바꿔야 할 때는 사람이 직접 고치고 양쪽에 알립니다. 설정 문법은 Claude Code 공식 문서(Hooks · Permissions) 기준입니다.

③ 지킬 것

  • 예외를 덧붙이지 않기: NEVER·IMPORTANT를 계속 추가하지 말고, 반복되면 settings.json으로 옮긴다
  • 복사 말고 가리키기: 긴 코드나 문서는 붙여 넣지 말고 경로(파일:줄)나 @파일로

# 기능: 회의록 요약과 담당자 배정

## 사용자 시나리오
- US1: 회의록을 올리면 요약을 본다
- US2: 할 일과 담당자가 자동으로 정리된다

## 요구사항
- FR-001 회의록(텍스트) 업로드

## 예외 규칙

# DESIGN.md
## 방향
- 업무 도구: 차분하고 빽빽하게, 강조는 한 곳만
- 참고 서비스: (references.md에서 고른 1~2곳)
- 컴포넌트 라이브러리: shadcn/ui

## 색
- MUST 토큰만 사용: --color-bg, --color-fg, --color-muted,
  --color-accent, --color-ok, --color-warn, --color-error
- MUST 본문 글자 대비 4.5:1 이상 (직접 계산해서 확인)
- SHOULD 상태 색은 강조색과 따로
- NEVER 토큰에 없는 색을 직접 쓰기

## 글꼴
- MUST --font-body, 숫자 열은 tabular-nums
- SHOULD 굵기는 2~3가지만

## 간격 · 모서리
- MUST 4px 단위 (--space-1 ~ --space-6)
- MUST 모서리는 --radius-sm, --radius-md 둘만

## 컴포넌트 · 상태
- MUST 모든 버튼에 hover·focus·disabled 상태
- MUST 화면마다 빈 화면·로딩·오류 상태 (contracts/ui-states.md)
- MUST 아이콘만 있는 버튼에 aria-label
- MUST 되돌릴 수 없는 동작은 확인 창
- NEVER 카드 안에 카드

## 움직임
- MUST transform·opacity만 애니메이션
- SHOULD 반응은 200ms 이하, prefers-reduced-motion 존중

예시 프로젝트(회의록 요약 앱) 기준입니다. 시점을 누르면 그 단계까지 생긴 파일만 보이고, 그 단계에서 새로 생기거나 고치는 파일이 표시됩니다.

시점

    설계 생기는 단계 · 같이 코드 UI 발표 누가 만드나 · 제안 표준이 아니라 이 정리에서 제안하는 파일 · NEW 이 단계에서 생김 · 수정 이 단계에서 고침

    만드는 것별 기본 세트

    위 워크플로는 기능이 여러 개인 웹앱 기준입니다. 작은 작업에 전부 붙이면 오히려 느려집니다.

    프로그램 (CLI · 백엔드)

    단계 뼈대 → 스펙 → 설계 → 구현 → 검증, 코드 칸만

    분리 필요 없음 (UI가 없음)

    파일 AGENTS.md spec.md plan.md tasks.md tests/

    절차형 묶음 하나와 TDD면 충분합니다.

    웹페이지 (랜딩 · 소개)

    단계 레퍼런스(선택) → DESIGN.md → 블록 조합 → audit

    분리 필요 없음, 한 세션으로 (로직이 거의 없음)

    파일 AGENTS.md DESIGN.md references.md reports/audit.md

    디자인 방향 스킬 하나 + shadcn + /impeccable audit

    웹앱 (기능 여러 개)

    단계 위 워크플로 전체

    분리 구현 단계에서 코드 세션과 UI 세션을 나눔 (또는 .claude/agents/에 서브에이전트 2개)

    파일 위 파일 트리 전체

    분리 효과가 가장 큽니다. 설계 단계의 contracts/와 tests/spec.md가 있어야 나눠도 끝에서 맞물립니다.

    발표 자료 (PPT)

    단계 내용 → 설계 → 제작 → 렌더 검사 → PDF와 함께 배포

    분리 필요 없음, 한 세션으로

    파일 outline.md deck.pptx 또는 index.html deck.pdf qa/

    받는 사람이 고쳐야 하면 pptx, 링크로 보여 주면 frontend-slides. 자세한 건 워크플로 탭의 발표 자료 트랙.

    공통 규칙

    • 한 세션에 켜는 스킬은 4~5개 이하 (절차형 1, 디자인 방향 1, 컴포넌트 도구 1, 검사 1)
    • 플러그인은 /plugin에서 프로젝트마다 켜고 끄기
    • 검증 안 된 추천이므로 같은 과제를 (1) 스킬 없이 (2) 섞어서 (3) 분리해서 만들어 비교하기

    작업별 조합

    A · 기존 프로젝트에 기능 추가 (코드만)

    /feature-dev→tdd→/qa

    공식 Feature Dev로 탐색·설계·리뷰 흐름을 잡고, 구현은 TDD로, 마지막에 실제 앱을 띄워 확인합니다.

    B · 새 서비스를 처음부터 (코드)

    /office-hours→/speckit.specify→/speckit.tasks→/speckit.converge

    만들 가치부터 따진 뒤 명세로 끝까지 관리합니다. 가볍게 가려면 Spec Kit 대신 OpenSpec.

    C · 화면이 있는 기능 (코드 + UI)

    /feature-dev→Nicelydone·SaaSFrame→/impeccable shape→shadcn MCP 블록→tdd→/impeccable audit+Vercel Skills

    코드 탐색과 화면 리서치를 같이 하고, DESIGN.md를 정한 뒤 블록으로 조립합니다. 로직은 TDD로, 화면은 감사로 마무리합니다.

    D · 돈 안 들이고 UI 시작

    • 설계·검증 단계: Impeccable
    • 구현 단계: shadcn 스킬 + shadcn MCP (다른 레지스트리도 연결 가능)
    • 검증 단계: Vercel Agent Skills

    뼈대 단계 라이브러리는 무료(shadcn·Ant Design·Tremor 중 하나). 스펙 단계는 Nicelydone·SaaSFrame의 무료 범위로 시작하고, 모바일 앱이면 Mobbin(유료)을 추가하세요.

    에이전트 지시문에 넣을 순서

    1. 코딩 전에 질문으로 빠진 조건을 채우고, 요구사항을 문서로 남길 것
    2. 화면이 있으면 레퍼런스 10장 이상을 모아 공통 패턴을 정리할 것
    3. 작업을 완료 기준이 있는 단위로 쪼개고, 계획과 DESIGN.md를 먼저 만들 것
    4. 로직은 테스트부터, 컴포넌트는 레지스트리 블록부터 찾을 것
    5. 끝내기 전에 실제 실행 확인, 독립 리뷰, 명세 대조, UI 감사를 할 것

    E · 제품 소개 발표

    spec.md+DESIGN.md→outline.md→pptx또는frontend-slides→렌더 QA→deck.pdf

    앱의 명세와 디자인 규칙을 그대로 가져와 같은 브랜드로 만듭니다. 받는 사람이 고쳐야 하면 pptx, 링크로 보여 주면 frontend-slides.

    F · 디자이너가 Figma로 작업하는 팀

    Figma 원본→get_variable_defs→DESIGN.md→Code Connect→get_design_context→get_screenshot비교

    디자인 원본이 하나(Figma)로 정해져 있을 때 가장 효과가 큽니다. 토큰을 먼저 옮기고, 컴포넌트를 연결한 뒤 화면을 코드로 옮기면 생성 코드가 우리 컴포넌트를 씁니다.

    피해야 할 조합

    • Superpowers + gstack + pstack 동시 설치: 셋 다 전체 절차를 끌고 가려 해서 충돌
    • brainstorming + grill-me 동시: 같은 질문을 두 번 받음
    • Spec Kit + OpenSpec 동시: 명세 파일이 두 벌
    • 디자인 방향 스킬 둘 이상 동시 (예: Impeccable + frontend-design): 디자인 방향 지시가 섞임
    • 컴포넌트 라이브러리 두 개 (예: Ant Design + shadcn): 버튼·표 모양과 토큰이 두 벌
    • Remotion + HyperFrames 한 프로젝트: React와 HTML 중 하나로 통일
    • pptx + frontend-slides를 한 덱에: 디자인 규칙이 충돌, 받을 형식 하나로
    • Figma 원본 + Stitch 시안을 동시에 기준으로: 기준 디자인이 두 개가 됨

    지금 이 상황이면 이 스킬

    지금 단계를 누르고, 상황을 누르면 설치 명령과 복사 버튼이 바로 펼쳐집니다.

    갈래
    조건에 맞는 상황이 없어요.

    프로그램·웹앱·웹페이지·발표 자료를 만들 때 꺼내 보는 치트시트입니다. 빠른 찾기에서 지금 상황으로 스킬을 찾고, 워크플로에서 단계별로 코드와 UI가 같이·따로 할 일을, Memory File에서 파일별 명령과 복사용 프롬프트를 봅니다.

    무엇을 왜 줄였나

    대시보드를 짧게 만들기 위해 32건을 정리했습니다. 기준은 네 가지입니다. ① 같은 단계·같은 갈래에서 역할이 겹치면 더 강한 하나만, ② 설치 명령을 확인하지 못했거나 유료·제한이 큰 것, ③ 같은 스킬을 여러 단계에 반복한 것, ④ 자리가 맞지 않는 것. 지운 내용은 아티팩트 버전 기록(이전 버전)에 그대로 남아 있습니다.
